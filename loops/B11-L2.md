# B11-L2 — Store schema + seed data (RLS hardening)

**Backlog:** B11 (PRD §12 Tier 5) · **Loop:** L2 · **Date:** 2026-08-07
**Previous loop:** B11-L1 (🔁 re-loop — blocking scrutinize finding)

## Why this loop exists

`B11-L1`'s scrutinize pass found a privilege escalation, and the main session
**reproduced both halves of it live** against the dev project as
`lungchat@store.test` (a `free`-tier seed store):

```
self-upgrade own store  -> [{"name":"ร้านลุงชาติ จตุจักร","package":"premium","status":"approved"}]
inject unvalidated item -> [{"name":"SCRUTINY-PROBE","affiliate_url":"javascript:alert(1)"}]
```

Both artefacts were deleted and the package restored immediately after.

Root cause: `create policy "Owners manage own store" … with check
(owner_user_id = auth.uid())` constrains **ownership only**. It says nothing
about `package` or `status`, and `FOR ALL` covers INSERT (where only `WITH CHECK`
applies) and UPDATE (where the old and new row both merely need the right owner).
So any authenticated user can:

- mint or upgrade themselves to `package = 'premium'` — the monetized lever
  (weight 8 vs 1) that `LOCAL-STORE.md` §7 says is admin-assigned only; and
- flip `status` from `'suspended'` back to `'approved'`, defeating B16 before it
  ships and breaking the PRD §3.11 criterion that suspended stores disappear.

Chained: with a store row, the `Owners manage own store items` policy (also
`FOR ALL`) allows unlimited `affiliate_products` INSERTs with **no zod, no
`httpUrl` refinement and no item cap** — B13's guards do not exist yet.
`getAffiliateProducts` does a bare `select("*")`, so injected rows render for
every user (`image_url` → `<img src>`, `affiliate_url` → `<a href>`). That is
stored XSS, and PRD §3.11 explicitly names `httpUrl` as the real boundary here.

Not covered by STORE-2: the seed PINs are an amplifier, not the vector — any
signed-in shopper reaches the INSERT path.

new `019` converges the already-migrated dev DB (018 is in `_migrations` and will
never re-run).

## Gate

lint ✅ · build ✅ · migration ✅ · renders ✅ (4 routes 200, 0 orphan `·`, 0 dev-log errors)

**Gate initially FAILED and was fixed twice within this loop:**

1. **Column revokes were inert.** `revoke ... (col)` cannot subtract from a
   table-level GRANT; Supabase grants table-wide INSERT/UPDATE/DELETE to
   `anon`/`authenticated` (confirmed via `information_schema.table_privileges`).
   The self-upgrade and role-flip both still succeeded. Fixed by
   revoke-then-regrant.
2. **The regrant broke profile editing for every user.** PostgREST's upsert emits
   `on conflict (user_id) do update set user_id = excluded.user_id, …` — the
   conflict key is in the SET list, so omitting `user_id` from the UPDATE grant
   made `upsertProfile`/`ProfileGate` fail with `permission denied`. Fixed by
   granting `user_id` (and `owner_user_id` on `stores`); RLS `WITH CHECK` still
   forbids reassignment — verified.

Post-fix, verified live as `lungchat@store.test`: package self-upgrade → denied ·
item insert → denied · role self-flip → denied · own-description edit → works ·
full 11-column profile upsert → works, `role` not clobbered.

## Scrutinize findings

- **BLOCKING** — `grant insert/update on public.stores to authenticated` ships the
  very write path this loop just deferred. Nothing writes `stores` through a
  user-scoped client until B12, and the grant is a direct PostgREST path that
  bypasses `store.functions.ts` and its zod/`httpUrl` entirely. **Reproduced:** as
  a store owner, wrote `logo_url = 'javascript:alert(1)'` with no validation. The
  plan's intended remedy ("add zod in B12") would NOT close it. — **open**
- **MAJOR** — `Public read approved stores` is granted to `public`, so `anon`
  reads every store with contact details using only the browser-inlined
  publishable key. Contradicts the settled decision recorded in PRD §12 B14 that
  `/store/$id` is not public. **Reproduced** via `curl` with no auth. — **open**
- **MINOR** — `019` rewrites store ids matching on `name`, the exact
  non-uniqueness this loop fixed elsewhere; a duplicate name rolls back all of
  `019`. — open
- **MINOR** — `019`'s "no-op on a fresh DB" comment is false for the FK swap;
  `018:31` should carry `on update cascade` itself. — open
- **MINOR** — column grants make any future `ADD COLUMN` on `stores`/`profiles` a
  trap; the tempting `grant update on <table>` one-liner silently restores this
  vulnerability. Needs a warning in `018` and `LOCAL-STORE.md` §3. — open
- **MINOR** — `seed-stores.ts` ownership update has no `.select()`, so zero
  matched rows report success. — open
- **NIT** — `anon` retains table-level write grants on `affiliate_products` (RLS
  neuters them, but they fail silently at 0 rows rather than erroring). — open
- Scrutinize also confirmed correct: grant-model completeness across all
  user-scoped writers, the `owner_user_id`/`user_id` reassignment attack does not
  work, DELETE revoke breaks nothing, `019` idempotency, 018+019 fresh ≡ dev, and
  the B13 deferral leaves no hole.
