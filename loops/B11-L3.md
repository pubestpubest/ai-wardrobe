# B11-L3 — Store schema + seed data (narrowed authorization)

**Backlog:** B11 (PRD §12 Tier 5) · **Loop:** L3 · **Date:** 2026-08-07
**Previous loop:** B11-L2 (⛔ escalated to the human — LOOP.md L3 trigger)

## Why this loop exists

L1 and L2 each ended on a blocking scrutinize finding, both the same shape:
**B11 pre-authorizing write paths for features that ship in B12/B13.** LOOP.md's
escalation fired (_"Scrutinize majors survive two re-loops (L3 reached) —
approach is wrong, stop and rethink with the human"_). The human chose to
continue with a narrowed scope rather than park or revert.

The insight that settles it: **B11 has no UI and no user-scoped writer.** It
therefore needs to grant `authenticated` nothing at all on `stores`. Every hole
so far came from granting ahead of need. A `GRANT` is a direct PostgREST path —
it bypasses `store.functions.ts` and its zod/`httpUrl` entirely, so "the
validation arrives in B12" was never a real remedy.

Reproduced before fixing (restored immediately after):

```
store owner writes logo_url = 'javascript:alert(1)'  -> accepted, no validation
anon curl with the browser-inlined publishable key   -> all 6 shops + contacts
```

## Plan (post-escalation)

1. **Remove both `grant insert/update … on public.stores to authenticated`** from
   `018` and `019`. Keep `revoke insert, update, delete`. B12 grants exactly the
   columns it needs, beside the validation that makes them safe.
2. **`Public read approved stores` → `for select to authenticated`.** It shipped
   as the default `public`; `anon` holds SELECT and the publishable key is inlined
   into the browser bundle, so every shop's phone/LINE/address was readable
   unauthenticated. PRD §12 B14 already settled that the store page is signed-in
   only — the migration simply failed to implement it. `019` drops and recreates
   to converge dev.
3. **Minor** — `019`'s id rewrites matched on the non-unique `name`; added
   `and not exists (select 1 from stores x where x.id = '<literal>')` so a
   duplicate name cannot collide the PK and roll back all of `019`.
4. **Minor** — `018` now declares the FK `on update cascade` at birth; `019`'s
   "no-op on a fresh DB" comment corrected.
5. **Minor** — warning in `018` that every future column
   on `stores`/`profiles` needs its own column-level GRANT, and that "fixing" a
   permission-denied with `grant update on public.stores to authenticated`
   silently restores this vulnerability.
6. **Minor** — `seed-stores.ts` ownership update gains `.select("id")` and throws
   when nothing matched; PostgREST returns `{data:null,error:null}` for zero rows,
   so it previously printed success and exited 0 even if `018` had never run.

`profiles` grants are unchanged and still required — `upsertProfile` writes 11
columns through the user-scoped client. Only `role` is excluded.

## Scrutinize findings

Verdict: **"the shipped SQL is correct — I found nothing wrong with the
migrations themselves."** All findings concerned the handoff to B12/B13, plus two
cheap defense-in-depth revokes. All fixed in this loop.

- **MAJOR** — `PRD.md` B13 told the next implementer _"RLS เป็นตัวบังคับ owner"_,
  but `019` deleted the only policy that would enforce it, and B12's entry never
  mentioned it must add the `stores` grants. Both would hit `permission denied` /
  RLS violation on first write, and the tempting one-line fix re-opens L1's hole.
  — **fixed**: both PRD entries now name the required grant/policy work.
- **MAJOR** — `LOCAL-STORE.md` §3 still described the pre-L3 model ("authorized by
  RLS"), and this doc claimed a warning had been added there that had not been.
  — **fixed**: §3 now documents RLS **and** column GRANTs, what B12/B13 each must
  add, the never-use-table-wide rule, and that `REVOKE (column)` cannot subtract
  from a table grant. This doc's false claim corrected.
- **MINOR** — `anon` retained table-level SELECT on `stores`; only the policy's
  `to authenticated` blocked it, while the sibling table's policy is
  `using (true)` — an easy pattern to copy wrongly. — **fixed**:
  `revoke select on public.stores from anon;` Anon now gets `42501` before RLS is
  even consulted.
- **MINOR** — `profiles` DELETE was never revoked: the third door in `role`'s
  wall. Inert today, but once B12 puts `role` on the `Profile` type a store
  account could delete its profile to shed `role='store'` and strand its store.
  — **fixed**: `revoke delete on public.profiles from anon, authenticated;`
- **NIT** — "grants `authenticated` NOTHING back on stores" overstated (SELECT and
  Supabase's default REFERENCES/TRIGGER/TRUNCATE remain). — **fixed** in the
  comment.

Confirmed correct by scrutinize: nothing in `src/` reads or writes `stores`
(zero references), `service_role` retains everything the seed path and B16 need,
the `profiles` grant list exactly matches `upsertProfile`'s payload, a suspended
store's owner can still read their own store, the `not exists` guard introduces
no bug, and — decisively — `migrate.server.ts:72`'s `sql.unsafe(body)` runs each
file under the simple query protocol as **one implicit transaction**, so `019` is
all-or-nothing and its four re-runs were safe. Fresh `018` alone ≡ dev's live
state, verified field by field.
