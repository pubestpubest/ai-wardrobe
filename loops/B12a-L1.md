# B12a-L1 — Store registration

**Backlog:** B12a (PRD §12 Tier 5) · **Loop:** L1 · **Date:** 2026-08-07
**Previous loop:** none (B11 ✅ shipped the schema this builds on)

Design source of truth: `LOCAL-STORE.md` §2/§3. Do not reopen settled decisions.

## Grill outcomes

- **Split approved.** B12 as written is ~10 files, past LOOP.md's ~400-line
  escalation trigger. Split into **B12a (registration)** and **B12b (shell)**,
  each independently gateable — B11's schema-only slice had no UI, needed a
  substituted gate, and that weak gate is part of why a privilege escalation
  survived to scrutinize.
- **`020` grants INSERT only.** UPDATE ships in B12b with the edit form that
  actually needs it. Directly applying B11's lesson: grant exactly what the loop
  ships, never ahead of need.
- **Post-registration = success panel on `/store/register`**, not a redirect —
  `/store` and the redirect guard are B12b. B12b replaces the panel with the
  redirect.
- **A small "เปิดร้านค้า?" link on the sign-in page.** Works naturally: `AuthGate`
  renders the login form regardless of pathname, so clicking it while logged out
  changes the URL, and signing in lands them on the register form.

## Plan (post-grill)

1. **`supabase/migrations/020_store_write_grants.sql`**

   ```sql
   grant insert (owner_user_id, name, description, contact_phone, contact_line,
                 contact_email, address, google_map_url, online_store_url,
                 logo_url, cover_url) on public.stores to authenticated;
   ```

   Column-level only — never `grant insert on public.stores`. `package`,
   `status`, `id`, `created_at` stay ungranted so defaults `'free'`/`'approved'`
   apply and neither can be set by the registrant. No UPDATE (B12b).

2. **`src/lib/store.functions.ts`** — `getMyStore` + `createStore`, both behind
   `requireSupabaseAuth`.
   - zod: `name` min 1; `httpUrl` on `google_map_url`, `online_store_url`,
     `logo_url`, `cover_url` (`LOCAL-STORE.md` §3 — with self-registered owners
     writing, this is the real XSS boundary, not a typo guard); `.refine` that at
     least one of phone / LINE / address is present.
   - **Refuse when the account already owns wardrobe items** — flipping `role`
     would strand their wardrobe behind B12b's redirect guard with the rows still
     theirs under RLS. "a deletion wearing a different hat" (`LOCAL-STORE.md` §2).
   - INSERT goes through `context.supabase` so RLS `with check (owner_user_id =
auth.uid())` applies. The `profiles.role` flip must use the **service-role**
     client: B11 revoked `role` from `authenticated` on purpose, so the server
     function is the only place that can set it.
   - **Ordering + repair:** insert the store first, then set the role. If the role
     write fails, the user owns a store while still `role='shopper'` — so
     `createStore` is idempotent: when the caller already owns a store it does not
     insert again, it re-asserts the role and returns the existing row. That makes
     a partial failure self-healing on retry instead of a dead end.

3. **`src/hooks/use-store.ts`** — TanStack Query wrapper, user-scoped key, mirroring
   `use-profile.ts`.

4. **`src/routes/store.register.tsx`** — the form (name, description, phone, LINE,
   email, address, map URL, online shop, logo, cover), Thai labels, inline
   validation mirroring the zod rules, and the success panel showing store name +
   package with a "หน้าจัดการร้านกำลังมาเร็ว ๆ นี้" note. Revisiting with a store
   already registered shows the panel, not a second form.

5. **Gating plumbing**
   - `role: "shopper" | "store"` on `Profile` + `DEFAULT_PROFILE` (`use-profile.ts`),
     and read it in `getProfile`/`mapRow` so it round-trips.
   - `ProfileGate` bypass on **`/store/register` exactly** — not `/store/*`. That
     is the only pathname where the role is still `shopper`; a prefix exemption
     would also cover `/store/$id`, which after B14 is a page shoppers reach from
     Discover, letting a new signup skip onboarding entirely.
   - Small link to `/store/register` on the `AuthGate` sign-in form.

Out of scope (B12b): `/store`, `/store/package`, StoreBottomNav, the `__root`
redirect guard, and the UPDATE grant.

## Implemented

- `supabase/migrations/020_store_write_grants.sql` — column-level INSERT grant.
- `src/lib/store.functions.ts` — `getMyStore` / `createStore`.
- `src/hooks/use-store.ts`, `src/routes/store.register.tsx`.
- `use-profile.ts` / `profile.functions.ts` — `role` round-trip (read-only).
- `ProfileGate.tsx` — `/store/register` bypass; `AuthGate.tsx` — sign-in link.

Implementer's own catch, worth keeping: its first pass flipped the role with
`.update()`, which no-ops silently when no `profiles` row exists yet — always
true for a brand-new signup, since `ProfileGate` is bypassed on this route so
`upsertProfile` never ran. Same PostgREST zero-rows trap B11-L3 fixed in
`seed-stores.ts`. Changed to an `upsert` that throws when nothing comes back.

## Gate

lint ✅ · build ✅ · tsc 7 = baseline ✅ · migration ✅ · renders ✅

Pen-tested the authorization layer live with a throwaway shopper account:
`package` injection → denied (column not granted) · `status` injection → denied ·
insert with another user's `owner_user_id` → RLS violation · legitimate insert →
defaults `free`/`approved` · UPDATE own store → denied (correct, B12b) ·
self-set `profiles.role` → denied. `column_privileges` showed INSERT on exactly
the 11 planned columns, no UPDATE/DELETE.

The **real** `CreateStoreSchema` (extracted from source, not reimplemented) was
run against `javascript:`/`data:`/`vbscript:` payloads, a missing contact channel
and an empty name — all rejected; LINE-only and an https URL accepted.

## Scrutinize findings

- **MAJOR-1** — the wardrobe guard is unreachable on the self-healing `existing`
  path, and `count && count > 0` falls open on `null`. — deferred to L2
- **MAJOR-2** — a column GRANT bounds columns, never values: a direct PostgREST
  insert bypasses zod entirely (reproduced — empty name + `javascript:` URLs
  accepted). — deferred to L2
- MIN-1 trailing-slash bypass · MIN-2 raw `23505` text · nits (double toast,
  `Partial<Profile>` accepting `role`, missing profile invalidation) — deferred
  to L2
- Confirmed correct: `upsertProfile` provably never writes `role`;
  `owner_user_id` can't be spoofed; the items count is RLS-scoped; scope
  discipline held (nothing from B12b leaked in).

## Decision

🔁 **Re-loop → B12a-L2** (two majors, both reproduced live).
