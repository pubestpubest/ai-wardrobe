# B12a-L2 — Store registration (value constraints + guard ordering)

**Backlog:** B12a (PRD §12 Tier 5) · **Loop:** L2 · **Date:** 2026-08-07
**Previous loop:** B12a-L1 (🔁 re-loop — two majors, both reproduced live)

## Why this loop exists

### MAJOR-1 — the wardrobe guard is unreachable on the repair path

`store.functions.ts:117-120` returns from the `existing` branch **before** the
`items` count at `:126`. The guard that `LOCAL-STORE.md` §2 calls "a deletion
wearing a different hat" never runs for an account that already owns a store row.

Non-adversarial path: the insert succeeds, `setRoleStore` throws, the user stays
`role='shopper'` and builds a wardrobe over the following week, retries
registration → `existing` is truthy → role flips → wardrobe stranded behind
B12b's redirect guard while RLS still says they own it. The self-healing path
added in L1 is what makes this reachable.

Adversarial variant: `020` lets a shopper with a wardrobe insert a `stores` row
directly, then call `createStore` → `existing` branch → role flipped, count never
run.

Also `if (count && count > 0)` **falls open on `null`** — an unparseable count
header lets the destructive conversion proceed.

### MAJOR-2 — a column GRANT restricts which columns, never what values

Reproduced live with a throwaway account, direct PostgREST, no server function
involved:

```
insert stores { name: "", logo_url: "javascript:alert(1)",
                google_map_url: "javascript:alert(1)",
                online_store_url: "data:text/html,<script>" }   -> ACCEPTED
```

Empty name, two `javascript:` URLs, a `data:` URL, and no contact channel — every
zod rule bypassed. `020`'s own header comment asserts the opposite ("grants back
exactly the columns createStore needs"), which restricts `package`/`status` — the
B11 escalation — but does nothing about _values_. `LOCAL-STORE.md` §3 carries the
same wrong premise: "beside the zod that makes those columns safe."

This is B11's lesson resurfacing one layer up: **whatever holds the grant is the
boundary.** zod in a server function protects nothing from a caller who can reach
PostgREST directly. Not live today — the `<a href>`/`<img src>` sinks arrive in
B14 — but B14 would inherit a boundary everyone believes is enforced.

## Plan

1. **`supabase/migrations/021_store_value_constraints.sql`** (new — `020` is
   already applied; no point duplicating into it). DB-level CHECKs, the only
   enforcement that survives a direct PostgREST call:
   - `google_map_url`, `online_store_url`, `logo_url`, `cover_url`:
     `is null or <col> ~* '^https?://'`
   - `length(btrim(name)) > 0`
   - `description` length cap
   - at least one of `contact_phone` / `contact_line` / `address` non-blank
   - Verified the 6 seeded stores already satisfy all of these (names non-empty,
     URLs https, every seed has `address` + `contact_line`), so the constraints
     apply cleanly to existing rows.
2. **`store.functions.ts`** — move the `items` count **above** the `existing`
   lookup so it guards every path, and change `count && count > 0` to
   `count !== 0` so a null count fails closed. Checked that no legitimate caller
   reaches `createStore` with items > 0: seeded accounts are already
   `role='store'` and never call it, and `store.register.tsx` only calls `create`
   when no store exists.
3. **MIN-1** — `ProfileGate` bypass is not trailing-slash safe; `/store/register/`
   would trap a shop behind the onboarding modal. Strip trailing slashes before
   the exact comparison (still not a `/store/*` prefix).
4. **MIN-2** — catch Postgres `23505` on the insert race and surface the Thai
   "คุณมีร้านค้าอยู่แล้ว" instead of a raw English constraint-violation string.
5. **Nits** — drop the duplicate error toast (keep `use-store.ts`'s `onError`),
   type `update` as `Partial<Omit<Profile, "role">>`, and invalidate
   `PROFILE_QUERY_KEY` after `createStore` so B12b's redirect guard sees the new
   role without a reload.
6. **Correct the false assurance** in `020`'s comment and `LOCAL-STORE.md` §3 —
   say plainly that column grants bound columns, CHECKs bound values, and zod
   bounds only what goes through the server function.

Deliberately NOT doing the scrutinizer's "simpler alternative" (drop the grant,
insert via service-role): it would move ownership enforcement out of RLS and into
handler code, against CLAUDE.md. Keeping RLS + grant + CHECKs.

## Scrutinize findings

- **MAJOR-1** — items guard unreachable on the self-healing `existing` path, and
  `count && count > 0` fell open on `null`. Reproduced by reading the control
  flow: `:117-120` returns before `:126`. — **fixed** (guard moved above the
  lookup; `count !== 0`).
- **MAJOR-2** — a column GRANT bounds columns, never values; zod was bypassable
  by direct PostgREST. **Reproduced live**: empty `name` + `javascript:` in two
  URL columns + `data:` URL + no contact channel, all accepted. — **fixed** via
  `021`'s CHECKs, plus corrected comments in `020` and `LOCAL-STORE.md` §3 that
  had asserted a protection they did not provide.
- **MIN-1** — `ProfileGate` bypass not trailing-slash safe; `/store/register/`
  would trap a shop behind the onboarding modal. — **fixed**.
- **MIN-2** — raw `23505` constraint text reaching a Thai UI. — **fixed**.
- **Nits** — double toast, `Partial<Profile>` accepting `role`, missing
  `PROFILE_QUERY_KEY` invalidation (B12b's guard reads it). — **all fixed**.
- Scrutinize's "simpler alternative" (drop the grant, insert via service-role)
  was considered and declined: it moves ownership enforcement out of RLS into
  handler code, against CLAUDE.md. Kept RLS + grant + CHECKs.
- Confirmed correct by scrutinize: `upsertProfile` provably never writes `role`
  (`ProfilePatchSchema` has no such key, zod strips unknowns) so B11-L2's
  regression does not recur; `owner_user_id` can't be spoofed (stripped by zod,
  pinned to `context.userId`); the items count is RLS-scoped per
  `012_scope_items.sql`; `setRoleStore`'s upsert works for an account with no
  profile row; the AuthGate link sits outside the `isWide` showcase so mobile
  gating and animations are untouched.

**Known gap, stated plainly:** `createStore` was never exercised over HTTP —
server-fn RPC ids aren't statically discoverable and no browser tooling is
available in this session. Its runtime behaviour (the refusal path, the repair
path, the role flip, UI error surfacing) is read-verified only. Everything
beneath it — grants, RLS, CHECKs — was pen-tested live, and the real
`CreateStoreSchema` was extracted from source and run against the payloads.
