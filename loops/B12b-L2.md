# B12b-L2 — Store shell (disabled-query load state)

**Backlog:** B12b (PRD §12 Tier 5) · **Loop:** L2 · **Date:** 2026-08-07
**Previous loop:** B12b-L1 (🔁 re-loop — one blocking, one major, same root cause)

## Why this loop exists

### BLOCKING — `/store/package` is unreachable by URL, refresh or bookmark

`use-store.ts:54-59` sets `enabled: !!session`. In TanStack Query v5
`isLoading = isPending && isFetching`, and a **disabled** query has
`fetchStatus: 'idle'` — so `isLoading === false` while `data === undefined`.

`AuthGate.tsx:49` renders children during SSR **and** during the client
auth-loading window. So on any hard load of `/store/package`:

1. no session yet → query disabled → `isLoading` false, `store` null
2. `store.package.tsx:33` takes the `!store` branch → `<Navigate to="/store" />`
3. `Navigate` runs in a `useLayoutEffect` (commit phase), while `useAuth`'s
   `getSession()` runs in a post-paint `useEffect` — **the redirect fires before
   the session is even requested**

A store owner who bookmarks or refreshes `/store/package` is bounced to `/store`.
The tab only works via an in-app `<Link>` from `/store`, where the cache is warm
— exactly the path that got exercised.

### MAJOR — `/store` flashes the registration form to an existing owner

Same root cause: on every hard load of `/store`, an owner with a live store sees
the **"สมัครร้านค้า"** card before it flips to the editor. Non-destructive if
submitted (`createStore` finds the existing row and returns it) but it should not
be reachable.

### My gate was wrong, and wrong in a familiar way

I saw `/store/package` return 200 with an empty body and reasoned "that's
`<Navigate>` rendering nothing during SSR — correct." I never asked _why_ `store`
was null. The evidence was already in front of me: `/store` SSR'd the
registration form rather than `กำลังโหลด…`, which proves `isLoading === false`
with no session. **A status code is not a render check.** Same shape as B11-L1,
where I asserted "no literal `null` in the markup" — a check that would have
passed with or without the change.

This repo has been bitten by this exact TanStack behaviour before; `use-wardrobe`
avoids it only because `wardrobe.tsx` checks `isLoading` before the empty state.

## Plan

1. **`src/hooks/use-store.ts`** — `isLoading: !session || isLoading`. One line,
   closes the blocker and the major together. No spinner-forever after logout:
   once `mounted && !loading && !session`, `AuthGate` returns the login screen
   _instead of_ children, so the store pages never render. Comment the trap so
   B13 doesn't reintroduce it.
2. **`StoreGuard.tsx`** — the `CRITICAL` comment states the hazard backwards.
   `DEFAULT_PROFILE` is `role: 'shopper'` and the guard only acts on
   `role === 'store'`, so the placeholder causes an **under**-redirect, never a
   wrong one. Keep the check (harmless, avoids a redirect on a stale read), fix
   the claim, and note that the flash it purports to prevent still happens
   because the guard is a post-render effect — the real lever would be
   `beforeLoad` on the shopper routes.
3. **`toRow()`** — one comment: full-replacement semantics, not patch. Every
   omitted field becomes `null`. True and safe today (`StoreForm` always sends
   all ten) but the endpoint's name reads like a patch.
4. **`getMyStore`'s `itemCount`** — note that it depends on
   `Public read catalog` staying `using (true)`. Flag for B13: **do not reuse
   this count for cap enforcement** — if that policy narrows, the count silently
   under-reports, and a quota check must use the service-role client.
5. **`StoreBottomNav`** — active state is `pathname === "/store"` exact, so
   `/store/` highlights nothing. Normalize, as `isStorePath` already does.
