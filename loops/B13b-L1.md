## Grill outcomes

- **RLS go received.** Policy + narrow column grants + CHECK constraints land in
  **one** migration. That ordering is the point: `023` already removed the
  table-wide write grants, so the policy is added against a table where only the
  granted columns are writable and CHECKs bound their values. `FOR ALL` with
  matching `using`/`with check`, not three per-command policies.
- **New `StoreItemModal`; `AffiliateEditModal` untouched.** The admin editor is
  wired to the service-role + `assertAdmin` path and requires marketplace fields.
  Keeping them separate stops the two authorization paths bleeding into one
  component — the split `LOCAL-STORE.md` §3 already draws.

## Plan (post-grill)

1. **`supabase/migrations/024_store_items_crud.sql`** — three things together:

   ```sql
   create policy "Owners manage own store items" on public.affiliate_products
     for all
     using (exists (select 1 from public.stores s
                    where s.id = affiliate_products.store_id
                      and s.owner_user_id = auth.uid()))
     with check (exists (select 1 from public.stores s
                         where s.id = affiliate_products.store_id
                           and s.owner_user_id = auth.uid()));

   grant insert (store_id, name, category, color, style, formality, price,
                 size, emoji, image_url, description, affiliate_url)
     on public.affiliate_products to authenticated;
   grant update (name, category, color, style, formality, price, size, emoji,
                 image_url, description, affiliate_url)
     on public.affiliate_products to authenticated;
   grant delete on public.affiliate_products to authenticated;
   ```

   - `store_id` is **insert-only** — items don't move between stores, and RLS
     alone would permit a move to another store the caller also owned.
   - `store` and `platform` stay **ungranted** — marketplace-only fields, nullable
     since B11; a local shop has no value for them.
   - DELETE has no column granularity, so the policy is what scopes it.

   CHECKs (the layer a grant cannot provide — B12a-L2):
   `image_url`/`affiliate_url` `is null or ~* '^https?://'` · `category` in the
   six · `formality` in the three · `length(btrim(name)) > 0` and a cap ·
   `price >= 0` · `description` cap. `category` is included because B13a-L1's
   scrutinize found it is free text today and an out-of-range value renders a
   blank label. **Verify the 50 existing rows satisfy every CHECK before adding.**

2. **`store-items.functions.ts`** — `createStoreItem`, `updateStoreItem`,
   `deleteStoreItem`, all behind `requireSupabaseAuth`, writing through
   `context.supabase` so RLS enforces ownership, and each additionally scoped by
   the caller's resolved `store_id`. zod mirrors the CHECKs (`httpUrl`, the two
   enums, non-blank name, non-negative price).

3. **Package cap** — count-then-insert in `createStoreItem`, **counted with the
   service-role client**, not the user-scoped one. B12b-L3: `getMyStore`'s
   `itemCount` reads through `Public read catalog`; if that policy ever narrows,
   a user-scoped count silently under-reports and a store slips past its cap.
   Cap from `STORE_PACKAGES[store.package].maxItems`. Keep the `ponytail:` note
   that count-then-insert is not atomic — a double-submit can land one over.

4. **`use-store-items.ts`** — add the three mutations, invalidating both the
   items key and the store key (`getMyStore.itemCount` feeds `/store/package`'s
   quota). Keep `isLoading: !session || isLoading` and `isError`.

5. **`StoreItemModal` + `/store/items`** — add / edit / delete with a
   confirmation, quota shown as `n/maxItems` with the add action disabled at the
   cap. Image: **upload or paste a URL**, reusing `uploadWardrobeImage`
   (`LOCAL-STORE.md` §6 — no new bucket). Fields: name, category, color, style,
   formality, price, size, emoji, image, description, optional product link.

Out of scope: B14 (Discover store cards, `/store/$id`), B15, B16.

### The gate found a cap bypass, fixed in-loop with `025`

The plan's cap was app-level `count-then-insert`, which assumed the server
function is the only writer. `024` granted INSERT, so that stopped being true:
**one direct PostgREST bulk insert put 17 rows in a free-tier (cap 10) store.**

Same lesson as B12a-L2, one level further out. zod bounds the server-function
path; column GRANTs bound which columns; CHECKs bound values; **nothing bounds a
count** — a row-level CHECK cannot see the rest of the table. And the cap is the
monetization lever, so an advisory cap is no cap. Human go taken before writing
the trigger.

Re-verified after `025`: bulk-15 → rejected, store unchanged at 2 · one-by-one →
8 accepted reaching exactly 10, 9th rejected · **service-role also capped** (no
privileged bypass) · `store_id is null` marketplace rows exempt. DB restored to
50 / 0 orphans / 18-12-9-5-4-2.

## Scrutinize findings

- **BLOCKING** — clearing an optional field silently didn't save, with a success
  toast. `toInput` emitted `undefined` for blanks and the handler treats
  `undefined` as "don't touch"; the refetch then made the value reappear. The fix
  needed **both** halves — emit `""` _and_ make the two URL schemas accept `""`,
  since `z.string().url()` rejects it, so a half-fix turns the silent no-op into
  a validation error. — L2
- **MAJOR** — the style field swallowed commas: `a` `,` `b` produced the single
  tag `ab`, because splitting on every keystroke round-trips to the same string
  and React resets the input. `style` is B15's AI-weighting input. — L2
- **MINOR** — zod didn't mirror the CHECKs, so raw English constraint strings
  reached the Thai toast (UI-reachable via a 20-char emoji and `price: 1e999`) ·
  zod failures rendered as a raw JSON blob · `024`'s CHECKs regressed B10's admin
  editor (its schema lacks `price >= 0` / `description` cap) · the `ponytail:`
  comment asserted the opposite of what shipped · non-UUID id leaked a Postgres
  type error. — all L2
- Scrutinize executed the server functions end-to-end (extracting fn ids from the
  built bundle) and independently closed a gap my 14-case matrix missed: insert
  with `store_id: null` **or omitted** → RLS-denied. That mattered because `025`
  exempts null `store_id` from the cap, so a permitted orphan would have bypassed
  the cap by a second door and landed in the Discover/AI catalog.
- It also proved `025`'s concurrency claim: 6 concurrent inserts at 9/10 → exactly
  one `201`, five rejected, final count exactly 10.
