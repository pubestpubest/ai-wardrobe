## Plan (post-grill)

1. **`getStorePublic`** in `src/lib/store.functions.ts` — takes a store id,
   returns the store profile + its items. Behind `requireSupabaseAuth`:
   `/store/$id` is **signed-in only, not public** (`AuthGate.tsx:49` gates every
   router route; PRD §12 B14 settled this). Read through `context.supabase` so
   RLS `Public read approved stores` applies — a suspended store is then
   invisible to everyone but its owner, for free and without an app-level check.
   Return `null` for a missing/suspended store rather than throwing.

2. **`src/routes/store.$id.tsx`** — the store detail page: logo/cover, name,
   description, contact rows (phone / LINE / email / address), map and online-shop
   links, package badge, and the full item grid. `store`/`platform` are never
   rendered. **Note the routing structure**: `store.tsx` is an `<Outlet/>` layout,
   so this becomes another child alongside `index`/`register`/`package`/`items` —
   which means `StoreGuard` already treats it as a store path, and a shopper
   reaching it is _not_ redirected. Good: shoppers are the intended audience.
   **`ProfileGate` must still gate it** — the bypass is `/store/register` exactly,
   deliberately not a prefix, so a brand-new shopper can't skip onboarding here.

3. **Four states**, in the order B12b-L2 established: loading → error → not-found
   → content. The hook must return `isLoading: !session || isLoading` and surface
   `isError`; a query disabled by `enabled: !!session` reports
   `isLoading === false`, which is what made `/store/package` redirect away.

4. **Admin store dropdown** — `AffiliateEditModal` gains a store `<select>` and
   `createAffiliateProduct`/`updateAffiliateProduct` write `store_id`. Without it,
   every admin-added item keeps `store_id = null` and disappears the moment B14b's
   filter and B15's AI-pool exclusion land. Needs a `listStoresForAdmin` server
   function behind `assertAdmin` (the service-role path — admins must see
   suspended and unclaimed stores too, which RLS would hide).
   `025`'s cap trigger exempts `store_id is null`, so an admin assigning a store
   now brings that item under the cap — expected, and worth a comment.

Out of scope: B14b (Discover regroup), B15, B16.

### The gate found a second cap bypass, fixed in-loop with `026`

`025`'s trigger was `BEFORE INSERT` only. An UPDATE relocating 18 items into a
free-tier (cap 10) store was **ACCEPTED**, leaving it at 20. **B14a is what made
that reachable** — `updateAffiliateProduct` now writes `store_id` via
service-role for the admin dropdown; store owners cannot (`store_id` is absent
from their UPDATE grant, GRANT-denied in B13b).

Treated as completing the trigger decision already taken in B13b, not a new one.
After `026`: the same UPDATE is rejected and the store stays at 2, **and** an
ordinary edit while a store sits at exactly 10/10 still succeeds — the
`when (new.store_id is distinct from old.store_id)` clause, without which every
edit would re-count a row already in the count.

Also verified directly (RLS, not app code, hides suspended stores): with a seed
store flipped to `suspended`, its **owner still sees it** and **another owner
does not**. Restored to `approved`.

## Scrutinize findings

The first scrutinize agent died mid-run on an API error. I verified the DB was
left untouched (6 stores approved, 50 products, 0 orphans, 18/12/9/5/4/2, 6
users), ran the one DB-mutating check myself, and re-ran scrutinize read-only.

**Verdict: fix-then-ship — nothing blocking.**

- **MAJOR** — a comment in `affiliate.functions.ts` declared the UPDATE cap gap
  "noted for the human, not fixed here" while `026`, which fixes it, shipped in
  the same change. Exactly the failure that bit B12b-L2 (whose `StoreGuard`
  comment had the hazard backwards); this repo uses comments as the loop-to-loop
  handoff, so a future loop would have re-written `026` or built a redundant
  app-level count. — **fixed**
- **MINOR** — a non-UUID `$id` threw a ZodError, driving the _error_ state with a
  "ลองใหม่" button that reloads into the identical failure forever. A malformed or
  stale link is semantically not-found. — **fixed** (`safeParse` → `null`)
- **MINOR** — `isError` was checked ahead of cached data, so a window-focus
  refetch failure replaced a fully-rendered page with the error screen. — **fixed**
  (`isError && !store`)
- **MINOR** — `getAffiliateProducts` had no auth middleware and reads via
  service-role with `select("*")`; B14a added `storeId` to `mapRow`, so
  unauthenticated callers were being handed the store→item mapping for every
  store. `LOCAL-STORE.md` §2 explicitly decided this data is signed-in only.
  — **fixed** (middleware added; every caller was already gated on `!!session`)
- **NIT** — the admin store `<select>` rendered blank until the list resolved.
  — **fixed** (disabled loading option)
- **NIT** — `storeId?: string` vs `storeId: string | null` type asymmetry. Noted.

Confirmed correct, with the mechanism traced rather than assumed: **the highest-
risk case — leaking a hidden store's items — does not occur**, because the
handler returns on `!row` _before_ issuing the items query, even though
`Public read catalog using(true)` would have made those items readable. `026`'s
`when` clause verified across all five old→new transitions, including that a
multi-row UPDATE is covered (a PL/pgSQL trigger's queries run read-write and see
the calling command's own changes, so row _k_ counts the k-1 already moved).
`assertAdmin` is the first statement in all four admin handlers.
`ProfileGate` still gates `/store/$id` (bypass is `/store/register` exactly).
Static routes correctly outrank `/store/$id`. B10, Discover and the AI path
unaffected.

**Two scope notes carried forward:** `/store/$id` has **zero inbound links** —
`AffiliateItemModal` still carries a "fallback link arrives in B14" comment, and
that belongs to neither half of the split; decide where it lands. And
`store.functions.ts` imports its `StorePublic` type from the client hook that
imports the function back — an erased cycle, but backwards.
