# B14b-L1 — Discover regroup into store cards

**Backlog:** B14b (PRD §12 Tier 5) · **Loop:** L1 · **Date:** 2026-08-07
**Previous loop:** none (B14a ✅ shipped `/store/$id` and the admin dropdown)

Design source of truth: `LOCAL-STORE.md` §5. Settled — do not reopen.

## Grill outcomes

- **B14b adopts `AffiliateItemModal`'s fallback link.** It belonged to neither
  half of the B14 split. B14b is the loop that makes `/store/$id` reachable from
  Discover, so every path to that page lands together. B14a already shipped both
  prerequisites (the route, and `storeId` on `AffiliateProduct`).
- **Shuffle is stable per visit, not per fetch.** Seed held in component state
  for the life of the mount, so the order is fixed while browsing, typing in the
  search box, or when a background refetch lands — and differs next visit. A
  window-focus refetch rearranging the page mid-scroll reads as a bug, not as
  fairness.

## Plan (post-grill)

1. **`getDiscoverStores`** in `src/lib/store.functions.ts` — behind
   `requireSupabaseAuth`; returns approved stores each with their items.
   **The exclusions must be server-side**, not filtered in the client:
   - suspended stores — read `stores` through `context.supabase` so RLS
     `Public read approved stores` does it (B14a proved this works: owner sees
     their suspended store, others don't);
   - `store_id is null` rows — admin-created marketplace items with no store.
     B14a's dropdown exists so new ones get a store; legacy nulls simply have no
     card. Note `affiliate_products` carries `Public read catalog using (true)`,
     so items are readable regardless — the grouping, not the item read, is what
     scopes this.
     Leave `getAffiliateProducts` alone: Home, Matches and StylistChat all use it.

2. **`src/hooks/use-discover-stores.ts`** — `isLoading: !session || isLoading`
   **and** `isError`. The B12b-L2/L3 trap: a query disabled by
   `enabled: !!session` reports `isLoading === false`, so a consumer takes its
   empty branch on a cold load.

3. **`src/routes/discover.tsx`** — regroup into store cards:
   - card header: logo, name, package badge; body: **up to 6 items**; footer:
     `ดูทั้งหมด (n) →` to `/store/$id` when the store has more than shown.
   - **order**: weighted by `STORE_PACKAGES[pkg].weight`, seeded from
     `useState(() => Math.random())` so it is stable for the mount.
   - **search matches store name as well as item name/description.** A
     store-name hit keeps that card with its **full** item list; an item-only hit
     narrows the card's contents. Once a shop's name is the largest text on the
     card, typing it and finding nothing reads as a bug.
   - **empty stores disappear** after filtering; the existing
     `ไม่พบไอเท็มที่ค้นหา` empty state fires when no store survives.
   - keep the category chips; keep the admin "เพิ่มไอเท็ม" affordance.
   - four states in the B12b order: loading → error → no-stores → content.

4. **`AffiliateItemModal`** — when an item has no `affiliateUrl` but has a
   `storeId`, show `ดูที่ร้าน` linking to `/store/$id`; external `affiliateUrl`
   still wins; neither → no button, as today. Removes the stale
   "fallback link arrives in B14" comment.

Out of scope: B15 (AI weighting — `findAffiliateProduct` untouched), B16 (admin
suspend + suspension enforcement).

## Scrutinize findings

**Verdict: fix-then-ship.** All fixed in L2 — no re-loop needed beyond it.

- **MAJOR** — `invalidate()` only touched `AFFILIATE_PRODUCTS_QUERY_KEY`;
  `DISCOVER_STORES_QUERY_KEY` was imported by nobody. Since Discover now renders
  from `getDiscoverStores`, an admin edit/delete/create toasted success while the
  card kept the old row — and it self-heals on refocus, which makes it _harder_
  to diagnose, not milder. Same silent-save class as B13b-L1. — **fixed**
- **MINOR** — `ดูทั้งหมด` was gated on the _filtered_ item count, so it vanished
  under any search or chip. For admin-created items (which always carry an
  `affiliateUrl`, so the modal shows the external link rather than `ดูที่ร้าน`)
  that was the **only** route from Discover to `/store/$id` — the page this loop
  exists to make reachable. Now gated and labelled on the store's full catalog:
  a navigation affordance should describe where it goes. — **fixed**
- **MINOR** — Discover pulled the whole catalog twice: `useAffiliateProducts` was
  mounted purely for `isAdmin`, and its products query had no `enabled` gate.
  Split out `useIsAdmin`. — **fixed**
- **NIT** — the header rendered `0 รายการ` directly above the error banner.
  — **fixed**

**Found while fixing, caused by my own B14a-L2 change:** the products query had
no `enabled` gate **and no session in its key**. Once B14a-L2 put
`requireSupabaseAuth` on `getAffiliateProducts`, it fired unauthenticated on cold
load, failed, and cached the failure with no refetch on login — affecting Home,
Matches and StylistChat. Gated and re-keyed.

Confirmed correct by scrutinize: the `.in()` empty-array footgun is unreachable
(early return on no stores); two queries, no N+1; `select("*")` on `stores` is
mapped down to 6 fields so no contact data or `owner_user_id` crosses the wire;
suspension exclusion is RLS, not app code; the four-state ordering closes the
`isError && hasData` case so a failed _background_ refetch keeps cached content;
`norm()`'s Thai-safe space-stripping preserved; store-name hit keeps the full
category-filtered list while an item hit narrows further; the 6-item cap applies;
`rise` staggers the card wrapper only, so no nested-stagger conflict; the
`useState(() => Math.random())` seed cannot cause a hydration mismatch because
the query is disabled during SSR; and every producer feeding
`AffiliateItemModal` sets `storeId`, so the fallback renders on all three
surfaces that mount it.
