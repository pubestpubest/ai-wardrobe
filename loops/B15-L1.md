# B15-L1 — AI recommendation weighting

**Backlog:** B15 (PRD §12 Tier 5) · **Loop:** L1 · **Date:** 2026-08-07
**Previous loop:** none (B14 ✅ shipped Discover cards and `/store/$id`)

Design source of truth: `LOCAL-STORE.md` §4. Settled — do not reopen.

## Grill outcomes

- **Shared helper in `wardrobe.ts`.** The weighting rule lives in one place next
  to `STORE_PACKAGES`, so Discover and the AI pool can't drift on what a package
  tier is worth. `discover.tsx`'s `weightedShuffle` moves there too.
- **One runnable check committed** (`scripts/check-weighting.ts`,
  `bun run check:weighting`). This is the monetization rule and it fails
  **silently** — nothing errors, a premium store just quietly stops winning, and
  the gate cannot see a distribution. LOOP.md's own upgrade path is "add a check
  when the gate misses its first real bug"; a distribution is a case the gate
  structurally can't catch.

## Plan (post-grill)

1. **`src/lib/wardrobe.ts`** — add `weightedPick(items, weightFn, rand)` and move
   `weightedShuffle` + the mulberry32 PRNG here from `discover.tsx`. `rand` is
   injected so the check can drive it deterministically. Both must handle: empty
   input, a single item, and all-equal weights.

2. **`findAffiliateProduct`** (`src/lib/affiliate.functions.ts`) — replace

   ```ts
   const pick = candidates[Math.floor(Math.random() * candidates.length)];
   ```

   with the **two-step** pick: group the tied candidates by `store_id`, weight the
   choice of **store** by `STORE_PACKAGES[pkg].weight`, then pick uniformly among
   that store's tied items.

   Why two-step and not per-item weighting (`LOCAL-STORE.md` §4): the two levers
   multiply. A premium store holds up to 20× more rows (200 vs 10) and each row
   would be 8× likelier — ~160× exposure, which is the hard-filter outcome
   reached by accident. Two-step pins the ratio at the package weight regardless
   of catalog size; a bigger catalog still helps honestly, by landing the store
   in more categories' pools.

   **Relevance still gates the pool** — this changes only the tie-break, so a
   premium store can never buy past a genuinely better match.

3. **Exclusions must be an explicit filter in the query.** This path uses
   `adminClient()` (service-role), so **RLS does nothing here** — the
   `Public read approved stores` policy that protects Discover is inert. Join to
   `stores` and require `status = 'approved'`; drop `store_id is null` rows.
   B14a's admin dropdown means new admin items get a store; 0 rows are null today.

4. **`scripts/check-weighting.ts`** + `"check:weighting"` in `package.json` —
   runs the real shared helper over a synthetic pool matching the seeded shape
   (1 premium / 2 basic / 3 free), asserts two-step lands near the weight ratio,
   and **also reports what per-item weighting would have produced**, so the
   160×-by-accident failure mode is visible rather than folklore. Non-zero exit
   on drift.

Out of scope: B16 (admin suspend + suspension enforcement — note this loop
already excludes suspended stores from the AI pool via the query filter, which is
the AI half of what B16 was told it owns; B16 keeps the banner and the refused
mutations).

## Scrutinize findings

**Verdict: fix-then-ship.** Both majors real; all fixed in L2.

- **MAJOR 1** — `scripts/check-weighting.ts` reimplemented the two-step
  _composition_ inline and imported only the leaf `weightedPick`, so it would
  have passed against a reverted `findAffiliateProduct`. The one artifact built to
  catch silent weighting drift was blind to it. — **fixed**: exported
  `weightedPickByGroup` and pointed both call sites at it.
- **…and my first fix was still insufficient.** Sabotage-testing it revealed the
  synthetic pool gave items in proportion to weight (20:8:8:2:2:2 ≈ 8:3:3:1:1:1),
  so "uniform per item" and "weight by package" produce the **same**
  distribution — the pool structurally could not tell them apart, and the check
  still printed OK. Inverted the pool (premium now has the FEWEST items) and made
  the comparison assertion direction-agnostic, since naive now undershoots rather
  than overshoots. **Now verified to catch all three plausible reverts**
  (uniform-per-item, naive-per-item, uniform-per-store) and to pass on correct
  code.
- **MAJOR 2** — B14a's store dropdown was optional and defaulted to
  `— ไม่ระบุร้าน —`. B15's null filter turned that into a silent hole: an admin
  saving without touching it created an item invisible in the AI pool and on
  Discover, yet still listed in the admin editor. — **fixed**: `storeId` is
  required by zod on create and the no-store option is gone.
- **MINOR** — the two-query fallback was unreachable (the FK has existed since
  `019`, so the embed always resolves) and it downgraded fail-loud to
  fail-quietly-then-retry. — **removed**.
- **MINOR** — `check:weighting` ran in no gate. — **wired into CI** beside lint.
- **MINOR, recorded not fixed** — the seeded data cannot exercise this feature:
  four of six category pools contain a single package tier, so the 8:1 weight is
  arithmetically inert there. Every claim about the mechanic rests on the check
  script, which is now load-bearing.

Confirmed correct: `weightedPick`'s edge cases all measured (empty → null, single
item at weight 0 or −5, all-zero → uniform, negative never wins, equal weights
uniform); `rand()` consumed exactly once per call on both branches; no float
overrun (stress-tested 10 000 items at `rand() = 0.99999999999`); scoring,
`bestScore` and `candidates` byte-identical so "a single strong signal wins
outright" still holds; the PostgREST embed returns an **object** not an array, so
`row.stores.package` is safe and the `package` CHECK makes an unknown key
impossible; `mapRow` enumerates fields explicitly so no `stores`/`status`/
`package` leaks into `AffiliateProduct`; `!inner` doesn't duplicate rows;
`wardrobe.ts` has zero imports so it stays client-safe; and `match-chat`'s two
call sites already guard a `null` return.
