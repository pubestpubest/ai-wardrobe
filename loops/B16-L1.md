# B16-L1 — Store admin + suspension enforcement

**Backlog:** B16 (PRD §12 Tier 5) · **Loop:** L1 · **Date:** 2026-08-07
**Previous loop:** none · **Last Local Store item** — after this only B08 remains.

Design source of truth: `LOCAL-STORE.md` §3/§7. Settled — do not reopen.

## Grill outcomes

- **RLS go received** to add `status = 'approved'` to the `Owners manage own
store items` policy. Checked first: the policy today filters on
  `owner_user_id` alone, so a suspended owner still holds the INSERT/UPDATE/
  DELETE grants from `024` **and** still passes the policy. An app-level refusal
  would be bypassable by one direct PostgREST call — the same class this feature
  has now had to fix four times (B12a-L2 grants-vs-values, B13b counts, B14a
  update-path cap, B15 service-role filter). **Whatever holds the grant is the
  boundary.**
- **Store-profile edits stay allowed.** Only item mutations are blocked. A
  suspended shop must still be able to fix its contact details — locking `/store`
  read-only would remove any route to remedy whatever caused the suspension.
- **Admin UI gets its own route, `/admin/stores`.** Admin tooling has outgrown a
  modal bolted onto a shopper page; this is the third admin capability.

## Plan (post-grill)

1. **`supabase/migrations/027_suspend_blocks_item_writes.sql`** — drop and
   recreate the policy with `and s.status = 'approved'` in **both** `using` and
   `with check`. Reads are untouched (`Public read catalog` is a separate
   SELECT policy), so a suspended owner still _sees_ their catalog on
   `/store/items` — they just can't change it. Comment must record why app-level
   refusal is insufficient, so a later loop doesn't "simplify" it back.

2. **`setStorePackage` / `setStoreStatus`** in `src/lib/store.functions.ts` —
   behind `requireSupabaseAuth` + `assertAdmin`, writing with the **service-role**
   client: `018`/`019` deliberately left `package` and `status` ungranted to
   `authenticated`, which is what stopped a store self-upgrading in B11-L2. zod:
   package in the three tiers, status in the two.
   **Note the interaction with `025`/`026`'s cap trigger:** an admin downgrading
   a store below its current item count is allowed (the trigger is
   `before insert`/`before update of store_id`, not on `stores`). The store then
   sits over quota and simply can't add more — `/store/package` already renders
   `18 / 10` in that state. Deliberate, and worth a comment.

3. **`/admin/stores`** — a route listing every store via the existing
   `listStoresForAdmin` (service-role, so suspended and unclaimed stores appear —
   RLS would hide them). Per row: name, package `<select>`, item count vs cap,
   and a suspend/reinstate action. Gate on `isAdmin` with a Thai not-authorised
   state; `assertAdmin` still fail-closes server-side, so the client gate is UX
   only. `listStoresForAdmin` currently returns `{id, name}` — extend it with
   `package`, `status` and an item count.

4. **Suspension banner + app-level refusal** — a Thai banner on `/store` and
   `/store/items` when `status = 'suspended'`, and a check in the item mutations
   that fails early with a readable message. This exists **for the message**;
   `027` is the enforcement. Same split as `025` vs the app-side cap check.

5. **Load-state discipline** (B12b-L2/L3): any new hook returns
   `isLoading: !session || isLoading` and surfaces `isError`; the route orders
   loading → error → empty → content.

Out of scope: B08.

## Scrutinize findings

**Verdict: fix-then-ship — no blocker.** The security spine was verified correct:
`027` is exact in both `qual` and `with_check`; `Public read catalog` is the
**only** SELECT policy on the table, which is _why_ reads survive replacing a
`FOR ALL` policy rather than that being luck; `authenticated`'s grants still
exclude `package`/`status`, so B11-L2's escalation stays closed.

- **MAJOR (pre-existing, made reachable by this loop)** — Home's
  `WardrobeUpgradeCard` sourced from `getAffiliateProducts`, a service-role
  `select("*")` with no status filter. So after an admin suspends a shop,
  Discover and the AI pool drop it but the **home page still recommends its
  items**, and `ดูที่ร้าน` links to `/store/$id`, which RLS hides — a live
  recommendation plus a dead link. — **fixed**: Home now sources from
  `getDiscoverStores` (RLS-filtered), the same move B14b made for Discover.
  `getAffiliateProducts` stays deliberately unfiltered — `matches.tsx` needs it
  to resolve historical `affiliateProductIds`, including from since-suspended
  stores.
- **MINOR** — `listStoresForAdmin` pulled every `store_id` row to bucket in JS;
  it under-reports the moment `db-max-rows` is set, and an admin uses that number
  to decide downgrades. — **fixed** (exact count per store, bounded by store
  count).
- **MINOR** — no `retry: false`, so a non-admin waited ~7s on `กำลังโหลด…` for a
  deterministic rejection. — **fixed**
- **MINOR** — nothing linked to `/admin/stores`. — **fixed** (link on Discover's
  admin controls)
- **NIT** — `StoreGuard` bounced any `role='store'` account off `/admin/*`,
  plausible for a seed login in `ADMIN_EMAILS`. — **fixed** (`/admin/*` exempt)
- **NIT** — `openEdit` wasn't gated on suspension while `openAdd` was. — **fixed**
- **Recorded, not fixed** — per-row pending state on `/admin/stores` (changing
  one row disables all), and `assertAdmin` imported across module boundaries
  (hygiene, no cycle).

**Design note raised by scrutinize:** `027` blocks DELETE as well, so a shop
suspended over an offending item can't remove it itself. Defensible — B10's admin
editor is service-role and can — but worth stating.
